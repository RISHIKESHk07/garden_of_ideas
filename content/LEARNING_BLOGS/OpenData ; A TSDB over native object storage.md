Few popular examples are wrapstream and turbopuffer for the architecture , in  the opposing corner we have Prometheus-compliant TSDB which are portrayed as expensive in setup ....
Opendata time series works on top of **slatedb** which was made by them , and here are some cost metrics for you , serve 4.7B samples/day over 3.3M active series for $500/month of compute costs.

We compare the cortex architecture here , mainly we have a semi stateful idea (meaning that we have a layer where we store some required metadata or temporary buffer , which means we cannot scale plainly like stateless where we have no data related but are just logical processing points which can be scaled infinitely , in case of semi stateful we have flush data to the storage layer using some consesus protocol , finally stateful which are just storage layer itself ). So over here in case of cortex and victoria metrics still use a stateful storage servers which require re replication , durability and rebalancing  , these operational challenges will persist . Now coming to our idea of using object stores as storage engines , we can use two servers; a writer and reader query server for this (recomended bois ...) and scale them effectively as required , a few operational advantages , node restarts do not effect anyone , ingestion throughput can be sped up using more writer nodes as its completely stateless , query throughput can be scaled by adding reader replicas and over here no orchestration is needed because readers hydrate caches straight from object storage while serving queries  , finally we can directly write into the object stores without cross availibility zones transfer fee being a problem ever (hack made into feature moment ...) .

We come to introduction of slateDB , which is basically a LSM storage engine written on top of object stores , general implementation is something crazy as turbopuffer and wrapstream 's LSM implementation is coupled with filesystem . The reason for a LSM tree storage engine being great for observibility stack is that we need fast writes which is provided by immutable nature of LSM trees , and indexing series map well with the default operations put/scan/get . For more details look up the design doc of TSDB .

Few tradeoffs for the end , cold reads are still a problem here when querying data which is not on the cache , and is slower compared to disk resident system , slateDB solves this by using a block cache memory (Foyer , rust based hybrid in-memory and disk cache ) , we have another layer over this again for historical queries and compaction can fold buckets together and merge samples accordingly . End-End write latency because fresh data sent to object stores are available after a while not immediately and also it actually slower than disk based approach which commits to a WAL and serves directly from local state , the reason  that this is not a problem in case of time series data obserbility stack  as its tolerable .
