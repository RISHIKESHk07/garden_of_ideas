# MY FINDINGS
- The main motive for making this kv storage engine was to make a simple interface which aligned more towards to cockroach DB requirements and remove the need for using Cgo , C binding lib for go which the CKDB team were using with their go based code for working with rocksDB .
- Rocksdb as a storage system is a major winner in the storage engine ecosystem many adapted versions made for many dbs , Myrocks for replacing innoDB (default storage engine) in Mysql etc.
- The CKDB labs started out with rocksDB due to its large utility and configurable structure , and performance but soon realised that as CockroachDB matured the needs from rocksDB started to not align well , essentially the bugs were always small but the mitigation was tiresome as the repo is 300k lines of c++ code to figure out why a issue occurred , and since the CKDB team used go as their primary language it was a entire new burden added to this .  
- Compaction was a bug highlighted in the blog here , mainly about using delete-range operation , and how rocksDB did not support this and they has to make a worse performant workaround 
- The main reason the decided to write their own version was, one they they used rocksDB based practices in their code making it quite diffcult to move towards other storage engines , even if they did the other engines question are not as suitable compared to rocks in the first place , the second important reason was to remove the c++ and go intermixing of code entirely and integrate it into the code properly in production . Making a fork and stripping features was a option but would have required effort more than the above options and finally end with something not as performant .
- They used a initial port of LevelDB 's go lang port to start out with ...
- Pebble resemble 's RocksDB in its API structure , its a LSM key-value store which provides SET,MERGE,DELETE RANGE,DELETE , can perform atomic batch solutions , read-only snapshots , internally it use a WAL and sstables etc .... search github for more ig
- Also the data written is buffered on a series of mem-tables which are implemented underhood as arena backed concurrent skiplist , which then flushed to disc as  sstables and then compacted in the background .
- It has some key differences in their implementation but are very similar ....
- They have maintain bidirectional compatibility with rocksDB meaning pebble can work with rocksDB generated Code and vice versa , it might be true as at point or the other they will devaite as pebble is not a full write up of rockDB in go but a subset of them .
- Idea of fuzzy testing mentioned where we test the system based on random input and wait for the system to crash to indicate some issue , but this not what we would like , and maintain a set of answers for all these random tests in hard , so move towards metamorphic testing where we test a feature on some number of different configurations (max size of sstables etc) of the system and check if the result is the same at the end , if their is a difference we figure out why ....
- For performance graphs look up the blog , the site 's mentioned workloads show that peblle is a tad bit greater than rocksDB in performance and some observable cases where it beats it entirely .
