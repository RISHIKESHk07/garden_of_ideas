### **MY FINDINGS:**

- Murat 's blog https://muratbuffalo.blogspot.com/2026/01/cockroachdb-serverless-sub-second.html , mentions key points and design breakdown over all details .
- The introduction of the paper explains what serverless is: _“automatic provisioning of compute + storage on demand by someone other than you.”_ It discusses the current (post-2020) structure of DBaaS offerings and their limitations in multi-tenant, multi-region storage scenarios. It highlights how co-sharing of data should be abstracted so that clients feel as though they are independent. It also talks about scaling down to zero and over-provisioning, along with cold start penalties in the order of seconds. Most solutions share hardware and software among users to amortize costs and allow fast scaling, but this introduces data security and performance challenges.
- To solve this, CRDB Labs introduced the concept of **cluster virtualization**, where an independent transactional CRDB cluster is a virtualized component of a larger shared physical cluster. They use a two-tier system: a SQL processing layer and a KV storage layer. Each client gets a separate SQL processing VM instance, allowing precise tracking of user costs. These SQL VMs run alongside others and interact with shared KV processes, providing similar security and performance as a single-tenant system. By not strictly dividing the system at the usual compute-storage boundary, they instantiate fewer resources during cold starts. This enables fine-grained sharing of compute and storage while maintaining sub-second cold starts, multi-region support, and full scale-to-zero capability.
- Related work in multi-tenant DB solutions includes **multi-variant architectures**. The simplest approach is running separate VMs per client, which is inefficient. A more cost-effective approach is sharing resources at various levels, which CRDB uses. Traditionally, separating compute and storage was a novel idea because databases had to scale vertically under high query loads regardless of dataset size. To address this, systems separated compute and storage across nodes. CRDB differs by using a shared KV layer that supports transactions, localized data placement, and replication. Data isolation is critical in multi-tenant architectures, along with rate limiting and performance isolation. Ensuring predictable performance despite noisy neighbors is an active research area, including smart tenant placement.
- Features of serverless systems include dynamic scaling of resources on demand. However, “infinitely scalable DBs” are limited by VM sizes in practice, so systems must abstract this limitation. CRDB achieves this by scaling horizontally across SQL and KV components rather than relying on VM size. Scaling to zero typically means shutting down unused services, but achieving sub-second cold starts in this scenario is challenging. Many systems maintain warm resources, which still incur costs. CRDB addresses this by using shared KV nodes that remain active without significant idle cost. **Continuous availability** is critical but difficult in serverless systems, as they must balance allocation across users while handling failures and maintenance. Features like live migration and transparent scheduling help maintain performance. Multi-region support varies in definition; some systems only provide read replicas, which still require constant provisioning. CRDB aims for more efficient multi-region behavior.
- In the single-tenant architecture of CRDB, the SQL layer handles API abstraction, query processing, and application services (e.g., HTTP). The KV layer implements a distributed transactional keyspace over physical storage nodes. The SQL layer converts requests into metadata and KV operations and communicates with the KV layer via RPCs. Data is stored as key-value pairs grouped into ranges (CRDB’s version of shards). When a range is not locally available, a gossip protocol helps locate it. For complex queries, DistSQL enables distributed execution to fetch data from the nearest nodes, reducing latency.
- In multi-tenant virtualization, two main ideas are used: logical storage partitioning and per-client SQL processes. Each tenant has its own SQL process interacting with a shared KV layer, ensuring that storage ranges are not shared across tenants. SQL processes include query planning, optimization, metadata handling, and application utilities. SQL isolation ensures that one tenant’s operations do not affect another. Internal prefixes are used in KV operations to separate tenant data, and these are stripped before responses are returned. A security boundary ensures that SQL processes can only access their own data. A system tenant acts as a superuser for managing virtual clusters and multi-region configurations. One bottleneck is cold-start latency of SQL nodes due to required network operations. CRDB addresses this using **table locality**:
    - Global tables for read-heavy workloads
    - Regional-by-row tables for write-sensitive workloads
    - Follower tables for stale reads  
        These optimizations reduce latency during startup and operation.
- In the serverless architecture, hybrid isolation is important, maintaining boundaries between SQL and KV layers for both compute and data isolation.
- Deployment is done using Kubernetes: client → proxy → SQL nodes → KV layer. The system shares resources across VMs. Capacity planning and per-tenant eCPU ensure performance isolation. The proxy handles routing, security, and dynamic load balancing, directing client requests to appropriate SQL nodes. It also manages scaling by adding or draining nodes. The autoscaler determines the number of SQL nodes based on recent usage patterns. Data is automatically resharded and redistributed as it grows. A warm pool of SQL nodes helps reduce latency. Dynamic session migration allows connections to move between nodes during scaling. Idle sessions are serialized with revival tokens, enabling seamless restoration without re-authentication. Multi-region support uses global DNS for geo-routing.
- Performance optimizations include improving cold start latency by allowing SQL nodes to reach a running state before certificates are fully ready. Autoscaling responsiveness was improved by replacing slower Prometheus-based monitoring with direct CPU-based metric collection.
- Performance isolation addresses overload in KV nodes. CPU and write bandwidth are the main bottlenecks. Solutions include rebalancing ranges across nodes (long-term) and fair resource allocation (short-term). Each node uses read and write queues organized as heaps per tenant. Scheduling prioritizes tenants with lower resource usage and enforces fairness using CPU time quanta. High-frequency sampling helps estimate queue lengths and manage CPU admission slots. Write bottlenecks arise from LSM-tree operations like compaction, and tools like Pebble are used to estimate per-operation costs.
- Tenant CPU attribution involves tracking both SQL and KV usage. While SQL usage is easy to measure, KV operations like compaction are harder to attribute. The system uses estimation models by breaking queries into smaller KV operations and distributing costs accordingly. CPU quotas are enforced using token bucket mechanisms.
- Evaluation shows that for OLTP workloads, serverless performs similarly to traditional systems. For OLAP workloads, traditional systems perform better due to overheads in distributed data processing. Other results are presented in the paper’s graphs.
- Overall, this is an interesting paper. A major takeaway is that much of the work focuses on adapting and optimizing existing systems rather than introducing entirely new ideas. It highlights that deep system understanding and targeted optimizations can be more practical than overly complex solutions—though in some cases, entirely new systems (like Pebble) may still be necessary.
