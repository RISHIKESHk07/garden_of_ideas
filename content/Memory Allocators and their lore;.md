gingerBill 's blog details about simple implementation of memory allocators from linear memory allocators (Arena) to stack allocators to Pool allocators to freeList allocators to Buddy allocators ,
The main motive of a memory allocators over normal mmap and sbrk shifting method is that we are not worried about carving virtual memory block for us to use (note mmap uses random blocks across the virtual memory , so we can't sequential assign the memory between two allocations which is a problem when we want to retrieve this memory for further use ) , but to efficiently manage these block for reuse without calling new system calls for new set of memory blocks , the main problem with reusing of memory is that when this set of memory blocks are spread throughout the virtual memory they can be just reused if we have similar memory block size requests coming in as well , but when not (larger mem requests or very smaller requests) they lead to external and internal fragmentation , stalling our allocator , this is solved by making sure the allocations are sequential and adjacent so then we can reclaim large block and coleseate them accordingly . These are few things to keeping in mind when building a memory allocator , Coming to types Arena allocators is a huge  block of memory buffer in which we crave out blocks as we need , it quite simple to use but we the constraint that we can free only the entire buffer all at once , so removing certain blocks only , This great when we need to remove and manage objects of similar lifetime as we can free all of them at once (game engines) . Next Stack pointers behave like our regular stack LIFO method and yes we can free any block here just we need make sure to remove everything which was allocated after it as well , something you see in RAII (c++) . Pool and freeList are similar , and their core agenda is that we allocate memory in specific chunks size only (no variable size in Pool) , and maintain a small header to maintain where the next free mem block is for allocation , this can lead to internal fragmentation but works great when you know the requirements of allocation properly , The free list here is linked list but get be implemented in RB trees for better look up (log N) .Finally Buddy allocator deals with internal fragmentation may repeatedly spliting the memory in two until the required mem block is less than half of the current split .

Above was simple idea of memory allocators , microsoft proposed a custom impl called minmalloc with its defining feature being that its uses three different free lists at different scope levels (thread lvl , local lvl , cross thread lvl) for managing the memory over a single global freelist which could be locked due to many requests at once , and then we have each thread having its own heap for allocation (figure this part out a bit more pls) , finally page stealing threads can "steal" pages from other threads that have finished their tasks, ensuring that memory doesn't remain trapped in an idle thread's local heap . A note this entire idea works on the principle of randomisation meaning that having these many freelist will result contention chances between two threads will be very low . (Check math proof)
